01 · 기능 동작 검증

명령을 실행하고,
결과로 확인한다

터미널은 글자로 컴퓨터에 요청하는 창입니다. 입력한 명령과 뒤에 나타난 결과를 함께 읽습니다.

Linux 명령쉬운 뜻확인 방법
pwd · ls -la · cd현재 위치 · 숨김 파일까지 목록 · 폴더 이동경로와 목록 확인
mkdir · touch폴더 생성 · 없던 빈 파일 생성목록과 0바이트 크기 확인
cp · mv · rm복사 · 이동/이름 변경 · 삭제복사본, 새 이름, 삭제 후 부재 확인
cat · chmod내용 읽기 · 접근 권한 바꾸기본문과 stat/ls 권한 확인
추가 검증 로그의 명령 · 실행용 시연 아님
mv -n -- source.txt renamed.txt
test ! -e source.txt
test -f renamed.txt
rm -- renamed.txt
test ! -e renamed.txt
실제 검증 기록

2026-11-07 별도 CLI 검증: 각 단계 exit=0. 이전 실습 사진과 하나의 연속 실행으로 묶지 않았습니다.

Docker 명령무엇을 확인하나
docker --versionDocker 클라이언트 버전
docker run hello-world컨테이너를 새로 만들어 테스트 메시지 실행
docker ps / docker ps -a실행 중 목록 / 종료된 것까지 전체 목록
docker images저장된 이미지 목록
git add저장할 변경 선택
→
git commit로컬 이력에 기록
→
git push원격 GitHub에 전송

run·add·commit·push는 상태를 바꾸는 명령입니다. 이 페이지의 복사 버튼은 명령을 실행하지 않습니다.

mv·rm 직접 실행 로그 ↗touch·0바이트 증빙 ↗hello-world 결과 ↗기존 Git Push 결과 ↗

03 · 핵심 기술 원리

같은 이미지에서 실행해도,
공간과 데이터는 구분된다

이미지는 앱과 실행 환경의 묶음이고, 컨테이너는 그 이미지를 실제로 실행한 인스턴스입니다.

Dockerfile이미지를 만드는 설명서
→
이미지실행 준비가 된 원본 묶음
→
컨테이너원본으로부터 실행한 별도 공간

포트: 서비스로 들어가는 입구

브라우저localhost:8090
→
호스트 매핑127.0.0.1:8090
→
Nginx 컨테이너80번 수신

8090:80은 호스트의 입구를 컨테이너 입구에 연결합니다. 컨테이너 안의 localhost는 그 컨테이너 자신입니다.

볼륨: 컨테이너 밖의 보관함

쓰기 컨테이너데이터 기록 후 삭제
→
Named Volume독립된 데이터 보관
→
새 컨테이너같은 내용 다시 읽기

Bind Mount는 호스트 폴더를 연결합니다. Named Volume은 Docker가 관리하는 저장 공간입니다. 컨테이너 삭제와 볼륨 삭제는 다릅니다.

권한·경로해석
r / w / x읽기 / 쓰기 / 실행. 디렉터리의 x는 내부 접근
644 = 6·4·4소유자 읽기·쓰기 / 그룹 읽기 / 기타 읽기
755 = 7·5·5소유자 읽기·쓰기·실행 / 나머지 읽기·실행
chmod 644 파일 · chmod 755 폴더접근 권한을 바꾸는 명령. 기존 파일 시연에 사용하지 않음
절대 경로 / 상대 경로/부터 시작하는 위치 / 현재 폴더 기준 위치
실제 검증 기록

Named Volume 추가 실습에서 컨테이너 삭제 전후 Codyssey volume persistence verified가 동일하게 출력됐습니다.

삭제 전 데이터 ↗컨테이너 삭제 ↗새 컨테이너 데이터 ↗디렉터리 권한 전후 ↗

04 · 문제 해결 과정

실패를 숨기지 않고,
연결 경로를 바꾸어 검증

같은 GitHub 저장소라도 연결 포트와 인증 세션이 다르면 결과가 달라질 수 있습니다.

  1. 증상SSH 22번에서 Connection reset. 사용자 터미널 기록.
  2. 가설연결 경로나 포트 제한 가능성을 검토. 정확한 차단 원인은 확정하지 않음.
  3. 대안ssh.github.com:443의 SSH 연결 사용. 웹 HTTPS 인증으로 바꾼 것은 아님.
  4. 검증사용자 터미널에서 계정 인증·원격 조회·dry-run 후 실제 Push 성공.
사용자가 제공한 실제 Push·후속 조회 출력 발췌
bf19ba0..b4fc41e main -> main
b4fc41e1ffdfeb1b0ca64ea2c08c22960faf5b44 refs/heads/main
Codex 세션의 Permission denied (publickey)·exit=128은 그대로 보존했습니다. 에이전트 접근은 세션 환경에 따라 달라질 수 있습니다. dry-run은 실제 Push와 다릅니다.
추가 점검해결·검증 원리
컨테이너 이름 충돌기존 codyssey-web-server가 Up임을 확인하고 삭제하지 않고 재사용
포트 충돌 예방사용 중인 매핑 확인 → 별도 포트·프로젝트 사용. 실제 포트 충돌 발생 사례로 주장하지 않음
데이터 영속성삭제 전 기록 → 컨테이너만 삭제 → 새 컨테이너에서 동일 내용 읽기. 데이터 유실 사고가 있었다고 주장하지 않음
SSH 성공·실패 출처 기록 ↗실제 이름 충돌과 기존 상태 ↗

05–1 · COMPOSE 단일 서비스

실행 방법도
파일로 관리한다

Compose는 여러 실행 옵션을 YAML에 모아 같은 방식으로 다시 실행하게 해주는 도구입니다.

구현 · 한 개의 Nginx 서비스

실제 파일 · docker-compose.yml
# 기존 Dockerfile과 HTML을 그대로 재사용합니다.
name: codyssey-m11-bonus1

services:
  web:
    build:
      context: ./web-server
    image: codyssey-m11-compose-web:bonus1
    ports:
      - "127.0.0.1:8090:80"

왜 필요한가

Nginx는 HTML을 HTTP로 전달하는 웹 서버입니다. 이미지·빌드 경로·포트 연결을 파일로 남기면 긴 실행 옵션을 다시 입력할 필요가 줄어듭니다.

web-server/Dockerfile + HTML
→
services.webCompose로 실행
→
localhost:8090컨테이너 80번으로 연결
실제 실습 명령 발췌 · up은 상태 변경
docker compose -f docker-compose.yml config --quiet
docker compose -f docker-compose.yml up --build --wait --wait-timeout 60
docker compose -f docker-compose.yml ps
curl --fail-with-body --silent --show-error --max-time 10 --include http://localhost:8090/
실제 검증 기록

YAML 검증 → 빌드·실행 → 상태·포트 → HTTP 200 순으로 확인했습니다. HTML 본문은 기존 파일 전체와 일치했습니다.

단일 서비스 설정 ↗실제 명령·출력·종료 코드 ↗

05–2 · 멀티 컨테이너

이름으로 찾고,
내부 네트워크로 통신

웹 서비스와 HTTP 점검용 보조 서비스가 같은 Compose 네트워크에서 연결됩니다.

구현 · probe 추가

실제 파일 · docker-compose.bonus2.yml
services:
  probe:
    # 기존 이미지의 wget을 HTTP 점검에 재사용합니다.
    image: codyssey-m11-compose-web:bonus1
    entrypoint: ["/bin/sh"]
    command: ["-c", "while :; do sleep 3600; done"]

같은 이미지를 재사용하지만 시작 명령은 셸 대기 루프입니다. probe는 Nginx 서버를 실행하지 않습니다.

왜 필요한가

컨테이너 IP를 직접 고정하는 대신 서비스 이름으로 요청하면 역할을 기준으로 연결할 수 있습니다.

probewget HTTP 점검
→
web:80Compose 내부 이름 해석
→
webNginx 응답

이 요청은 호스트의 8090번을 거치지 않습니다. probe에는 공개 포트가 없습니다.

실제 실습 명령 · 기존 web 유지, probe만 추가
docker compose -f docker-compose.yml -f docker-compose.bonus2.yml up --no-deps --no-build --pull never --wait --wait-timeout 60 probe
docker compose -f docker-compose.yml -f docker-compose.bonus2.yml exec -T probe wget -S -T 10 -O - http://web:80/
실제 검증 기록

두 서비스 Up · 같은 네트워크 · 내부 HTTP 200 · HTML 일치 확인. 기존 web의 ID·시작 시각·포트도 유지했습니다.

docker top … -eo comm,args는 PID 필드 조회 오류로 exit=1입니다. HTTP 검증 뒤의 보조 조회 실패이며, 통신 실패로 해석하지 않습니다.

보조 서비스 설정 ↗내부 통신·실패 기록 ↗

05–3 · COMPOSE 운영

실행 → 관찰 → 로그 →
정리까지 확인한다

원래 서비스 대신 독립 프로젝트에서 운영 명령을 검증해 기존 미션을 보호했습니다.

up서비스 실행
→
ps실제 Up 확인
→
logs시작 메시지 확인
→
down전용 자원 정리

구현 · 임시 프로젝트

실제 파일 · docker-compose.bonus3.yml
name: codyssey-m11-bonus3-ops

services:
  ops:
    # 기존 이미지를 재사용하며 서버 포트는 공개하지 않습니다.
    image: codyssey-m11-compose-web:bonus1
    entrypoint: ["/bin/sh"]
    command:
      - "-c"
      - |
        echo 'CODYSSEY_COMPOSE_OPS_READY'
        while :; do sleep 3600; done

왜 필요한가

실행만 되는지 보는 데서 끝나지 않고, 상태와 로그를 읽고 어떤 자원이 정리됐는지 확인하는 운영 습관입니다.

실제 logs 출력
ops-1  | CODYSSEY_COMPOSE_OPS_READY

up의 대기 성공만으로 판단하지 않고 ps와 메시지를 각각 확인했습니다. 서비스 준비 기준은 이 실습의 시작 메시지입니다.

실제 실습 순서 · down은 종료·삭제, 발표 시연용 아님
docker compose -p codyssey-m11-bonus3-ops -f docker-compose.bonus3.yml up --no-build --pull never --wait --wait-timeout 60
docker compose -p codyssey-m11-bonus3-ops -f docker-compose.bonus3.yml ps
docker compose -p codyssey-m11-bonus3-ops -f docker-compose.bonus3.yml logs --no-color --tail 50 ops
docker compose -p codyssey-m11-bonus3-ops -f docker-compose.bonus3.yml down
실제 검증 기록

네 명령 exit=0. 정리 후 임시 컨테이너·네트워크 0개. 기존 컨테이너 8개와 네트워크·이미지 유지.

독립 운영 설정 ↗운영·정리 결과 ↗

05–4 · 환경 변수

코드는 그대로,
서버의 실제 포트는 변경

환경 변수는 프로그램에 외부에서 전달하는 설정값입니다. 여기서는 NGINX_PORT 숫자만 바꿉니다.

.envNGINX_PORT=8091
→
Compose치환 + 컨테이너 전달
→
템플릿 → Nginxlisten 8091;

구현 · 변수 전달과 포트

실제 파일 · docker-compose.bonus4.yml
name: codyssey-m11-bonus4-env

services:
  web:
    image: codyssey-m11-compose-web:bonus1
    environment:
      NGINX_PORT: "${NGINX_PORT:?NGINX_PORT is required}"
    ports:
      - "127.0.0.1:${NGINX_PORT}:${NGINX_PORT}"
    volumes:
      - ./bonus4-env/default.conf.template:/etc/nginx/templates/default.conf.template:ro

왜 필요한가

HTML이나 이미지를 다시 만들지 않고 실행 환경에 맞게 설정을 바꿉니다. .env는 Compose 치환 입력이고, 컨테이너 전달은 environment 설정이 맡습니다.

실제 파일 · bonus4-env/default.conf.template
server {
    listen ${NGINX_PORT};
    server_name localhost;

    location / {
        root /usr/share/nginx/html;
        index index.html;
    }
}

개인키로 인증한다

Ed25519는 이 실습에서 선택한 SSH 키 방식입니다. 공개키는 GitHub에 등록하고 개인키·암호문은 로컬에서 보호합니다.

구현 · 전용 키와 SSH 443

개인키 권한 600, 공개키 644. 공개키는 GitHub 계정에 등록했습니다. origin은 HTTPS로 유지하고 명령에서 SSH URL을 지정했습니다.

왜 필요한가

매번 토큰을 명령에 넣지 않고 키로 신원을 확인합니다. SSH 에이전트는 키를 사용할 수 있게 돕는 세션 도구이며, 다른 터미널·프로세스에서 공유되지 않을 수 있습니다.

Codex의 SSH 인증 실패 exit=128은 로그에 남겨뒀습니다. 이번 자료 제작 직전에는 HTTPS 원격 조회로 로컬·원격 main 33b0e448… 일치를 직접 확인했습니다. HTTPS 조회는 SSH 인증 성공의 대체 증거가 아닙니다.
